You are the principal software engineer responsible for creating, documenting, and evolving a gamified learning application for software developers.

The product should provide an experience similar to Duolingo, but focused on developers who want to practice software engineering knowledge every day.

Before writing any code, read this entire specification, define an incremental implementation plan, and create the permanent documentation and instruction files described below.

# 1. Product goal

Create a responsive web application, prepared for a future transition to a Progressive Web App, where developers can:

* Create an account and authenticate.
* Choose a learning path.
* Complete an initial placement test.
* Receive personalized daily sessions.
* Answer technical questions.
* Receive explanations after each answer.
* Earn XP.
* Maintain a daily streak.
* Improve their mastery of individual skills.
* Track statistics and progress.
* Compete in rankings in the future.
* Review content using spaced repetition.
* Resume interrupted sessions.
* Clearly understand which skills they have mastered and which skills require further review.

The first available learning path will be:

Java Backend Developer

It may contain skills such as:

* Java.
* Object-oriented programming.
* Collections.
* Concurrency.
* Spring Boot.
* REST APIs.
* SQL.
* PostgreSQL.
* NoSQL databases.
* Testing.
* Git.
* Docker.
* AWS.
* Messaging.
* Observability.
* System Design.

Do not create hundreds of questions at this stage. Create only a small amount of high-quality initial content that demonstrates the complete application flow.

# 4. Architectural principles

Initially implement the application as a modular monolith.

Do not create microservices prematurely.

Use Hexagonal Architecture principles, also known as Ports and Adapters.

Clearly separate:

* Domain.
* Use cases.
* Ports.
* Input adapters.
* Output adapters.
* Infrastructure.
* Configuration.

The domain must not depend on:

* Spring.
* JPA.
* Supabase.
* Render.
* Vercel.
* Email providers.
* Queue providers.
* Storage providers.
* User interface libraries.

Dependencies must point toward the application core.

Organize the backend by business modules rather than only by global technical layers.

Example modules:

* identity
* users
* learning
* questions
* sessions
* progress
* gamification
* administration

Each module may internally contain:

* domain
* application
* adapters
* configuration

Avoid creating a global package structure containing hundreds of classes grouped only into:

* controllers
* services
* repositories
* entities

Protect module boundaries with architecture tests when appropriate.

# 5. Portability and low coupling

The application must be designed to allow external providers and infrastructure components to be replaced in the future.

## Database

Do not write business rules that depend on PostgreSQL-specific features unless there is a documented justification.

Use repository interfaces inside the application core.

JPA implementations must remain inside infrastructure adapters.

Do not expose JPA entities directly through controllers.

Do not use persistence entities as domain models when doing so would create inappropriate coupling.

Explicitly distinguish between:

* Domain entity.
* Persistence entity.
* Input DTO.
* Output DTO.

When complete separation would add unnecessary complexity, document the decision in an Architecture Decision Record.

## Authentication

Create an abstraction similar to:

IdentityProvider

It should support operations such as:

* Validating a token.
* Retrieving the authenticated identity.
* Resolving an external identifier.
* Linking an external identity to an internal user.

Initially implement:

SupabaseIdentityProvider

The application domain must work with the internal user identifier rather than Supabase-specific objects.

A future migration to Auth0, Clerk, Keycloak, Cognito, or a custom authentication implementation must not require significant changes to the domain.

## Notifications

Create a notification port when there is an actual external boundary, even if the MVP only contains a local implementation or no real external integration.

Example:

NotificationGateway

Future implementations may use email, push notifications, or another provider.

Do not create unused abstractions only for formality. Introduce ports where a real external boundary exists.

## File storage

If file storage becomes necessary in the future, use a storage abstraction.

Do not couple business logic directly to Supabase Storage.

## Time

Do not directly call the system clock inside business rules.

Inject a time abstraction such as:

ClockProvider

Use an implementation based on `java.time.Clock` in production.

This is necessary for reliably testing:

* Daily streaks.
* Expiration.
* Daily limits.
* Sessions.
* Spaced repetition.

## Identifiers

Do not make the domain depend on database-specific sequences.

Prefer UUIDs for public and internal identifiers unless another choice is explicitly justified and documented.

# 6. Twelve-Factor App principles

The application must follow the Twelve-Factor App methodology.

Apply the following principles explicitly.

## Codebase

* Maintain one version-controlled codebase.
* Produce different deployments from the same codebase.
* Initially use a monorepo with separate frontend and backend directories.

## Dependencies

* Declare every dependency explicitly.
* Include Maven Wrapper for the backend.
* Commit the frontend lockfile.
* Do not rely on implicit dependencies installed in the local environment.

## Configuration

* Provide configuration through environment variables.
* Never store secrets in source code.
* Never commit secrets.
* Create only `.env.example` files without real secret values.
* Validate required environment variables during startup.

## Backing services

* Treat the database, authentication provider, email provider, storage provider, and other integrations as replaceable external resources.
* Provide URLs and credentials through configuration.

## Build, release, and run

* Clearly separate build and execution.
* Do not modify source code during application startup.
* Document the migration strategy used during deployments.
* The same artifact must run in different environments using different configurations.

## Processes

* Keep the backend stateless.
* Do not depend on persistent local files.
* Do not store important session state only in memory.
* Store persistent state in appropriate backing services.

## Port binding

* Expose the backend through the port provided by the environment.
* Respect the `PORT` environment variable used by Render.

## Concurrency

* Allow horizontal scaling of the backend.
* Do not depend on in-memory singletons for user state.
* Future scheduled jobs must account for multiple running instances.

## Disposability

* Start quickly.
* Shut down gracefully.
* Handle termination signals appropriately.
* Important operations must be transactional or idempotent.

## Development and production parity

* Minimize differences between development, test, and production environments.
* Use PostgreSQL in integration tests through Testcontainers.
* Do not use H2 to simulate PostgreSQL-specific behavior.

## Logs

* Send logs to stdout and stderr.
* Use structured logging.
* Do not store important logs only in local files.
* Never log passwords, access tokens, refresh tokens, or sensitive data.

## Administrative processes

* Version administrative scripts.
* Execute seeds and migrations in a controlled and documented way.
* Do not rely on undocumented manual changes.

# 8. Mandatory AGENTS.md file

Create a file named `AGENTS.md` in the repository root.

This file will be the primary source of permanent instructions for every AI coding agent working on the project.

The `AGENTS.md` file must include at least the following rules.

## Mandatory reading

Before making any change, the agent must read:

1. `AGENTS.md`
2. `README.md`
3. `docs/ARCHITECTURE.md`
4. The code and tests related to the requested change.
5. Any ADRs related to the affected area.

## Testing rules

* Never delete tests only to make the build pass.
* Never disable tests with `@Disabled`, skip flags, comments, or equivalent configuration without explicit authorization.
* Never weaken an assertion only to accept incorrect behavior.
* Never modify a valid test to hide a regression.
* When behavior intentionally changes, update the tests and document the reason.
* When a test becomes obsolete, explain why it is obsolete before removing it.
* Whenever possible, replace a removed test with another test representing the new behavior.
* Every bug fix must include a regression test that fails before the fix and passes after it.
* New business rules must include unit tests.
* Database integrations must include integration tests when appropriate.
* Critical user flows must include end-to-end tests.
* Do not consider a task complete while tests are failing.
* Do not ignore flaky tests. Investigate their root cause.

## Architecture rules

* Do not create dependencies from the domain to frameworks or external providers.
* Do not couple business rules to Supabase.
* Do not allow the frontend to directly access the database for core business operations.
* The frontend must consume the backend API for the main application rules.
* Do not expose persistence entities through the API.
* Do not place significant business logic in controllers.
* Do not place significant business logic in React components.
* Do not introduce microservices without an approved architectural decision.
* Do not add a new library without justifying its necessity.
* Do not create speculative abstractions without a real boundary or use case.
* Preserve API compatibility or clearly document breaking changes.
* New dependencies between modules must respect architectural boundaries.

## Database rules

* Every schema change must use Flyway.
* Never edit a migration that may already have been executed in another environment.
* Create a new migration to correct or evolve the schema.
* Never rely only on manual changes made in the Supabase dashboard.
* Never store secrets in the database or source code.
* Analyze backward compatibility for migrations used during deployment.
* Prefer migrations that support zero-downtime or low-risk deployment strategies.

## Documentation rules

* Update documentation whenever application behavior, architecture, configuration, API design, or development workflow changes.
* Update `docs/API.md` when endpoints are added or modified.
* Update `docs/DATA_MODEL.md` when entities or relationships change.
* Update `docs/ARCHITECTURE.md` when important components or dependencies change.
* Create or update an ADR for significant architectural decisions.
* Update `.env.example` whenever an environment variable is added.
* Never include real secrets in examples.
* Keep the source code and documentation consistent.

## Security rules

* Never log access tokens, refresh tokens, passwords, or secret keys.
* Never expose internal stack traces directly to API clients.
* Validate every external input.
* Enforce authorization in the backend.
* Do not rely only on frontend visibility controls.
* Apply the principle of least privilege.
* Do not trust user identifiers sent by the client as the authenticated identity.
* Resolve the authenticated user from the validated token.
* Protect administrative endpoints by role.
* Never use the Supabase service role key in the frontend.

## Mandatory change process

For every task:

1. Understand the requirement.
2. Inspect the existing code.
3. Identify the affected modules.
4. Identify risks.
5. Write or update tests.
6. Implement the smallest coherent change.
7. Run the related tests.
8. Run the complete test suite when feasible.
9. Run linting and type checking.
10. Update documentation.
11. Summarize the changes.
12. Report the commands executed and their results.
13. Report real risks or pending work.

## Prohibited behavior

* Do not claim that something was tested unless the test was actually executed.
* Do not invent files, endpoints, or application behavior that do not exist.
* Do not hide errors.
* Do not modify unrelated files without a clear reason.
* Do not reformat large parts of the project during a small change.
* Do not add dead code.
* Do not leave TODO comments without context.
* Do not use magic values when configuration or constants are more appropriate.
* Do not create silent fallbacks for mandatory configuration.
* Do not perform destructive changes without explaining their impact.

## Definition of done

A task is complete only when:

* The requirement has been implemented.
* Tests have been created or updated.
* Relevant tests pass.
* Linting passes.
* Type checking passes.
* Applicable documentation has been updated.
* No secrets are present in the source code.
* The code respects architectural boundaries.
* Relevant decisions are documented.
* The agent clearly reports what was completed and what could not be verified.

# 11. Daily sessions

Daily session generation must:

* Consider the skills in the learning path.
* Consider the current user level.
* Prioritize skills that need review.
* Include new content when appropriate.
* Avoid immediately repeating the same questions.
* Be deterministic when required for testing.
* Allow sessions to be resumed.
* Avoid creating a new active daily session when one already exists, unless an explicit rule allows it.
* Be idempotent for repeated requests.
* Persist the selected questions so the session does not change while the user is completing it.

Completing a session must:

* Record answers.
* Update progress.
* Grant XP exactly once.
* Update the streak exactly once.
* Produce a session summary.
* Be transactional.
* Be safe against duplicate requests.

# 12. Authentication and authorization

Use Supabase Auth initially.

Expected flow:

1. The frontend authenticates the user through Supabase Auth.
2. The frontend receives an access token.
3. The frontend sends the token to the backend using the `Authorization` header.
4. The backend validates the token.
5. The backend resolves the external identity.
6. The backend finds or creates the internal user.
7. Application use cases operate using the internal user identifier.

Do not trust the frontend to determine roles.

Implement at least:

* USER role.
* ADMIN role.

Do not expose administrative endpoints to regular users.

Clearly document how tokens are validated.

# 23. Expected agent behavior

Before starting any stage:

1. Read the existing rules and architecture documents.
2. Inspect the repository.
3. State which files are expected to change.
4. Explain the goal of the stage.
5. Identify risks and decisions.
6. Implement only the current stage scope.
7. Run available verification commands.
8. Update documentation.
9. Present a final summary.

When completing a change, report:

* What was implemented.
* Main files changed.
* Decisions made.
* Tests added.
* Commands executed.
* Test results.
* Pending work.
* Risks.
* Recommended next step.

Do not respond only with “done.”

Do not claim that commands were executed when they were not.

When something cannot be executed or verified, state the limitation clearly.
